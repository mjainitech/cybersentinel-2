# CyberSentinel API

Backend for the Website Scanner. Holds every third-party API key —
the frontend never sees a secret, it only ever talks to this server.

## Setup

```bash
cd server
npm install
cp .env.example .env   # then fill in whichever API keys you have
npm run dev
```

Server starts on `http://localhost:8787` (configurable via `PORT`).

## Endpoint

`POST /api/scan`

```json
// Request
{ "url": "https://example.com" }

// Response — see src/types.ts for the exact shape
{
  "url": "https://example.com/",
  "score": 88,
  "band": "safe",
  "recommendation": "This website appears safe.",
  "checks": [
    { "id": "https", "title": "HTTPS Enabled", "value": "Enabled", "summary": "...", "status": "safe" }
    // ...one entry per check
  ],
  "meta": {
    "partial": false,
    "unavailableChecks": [],
    "cached": false,
    "scannedAt": "2026-08-03T12:00:00.000Z"
  }
}
```

## What powers each check

| Check                          | Source                                  | Needs a key? |
| ------------------------------- | ---------------------------------------- | ------------ |
| HTTPS Enabled                   | Direct TLS probe (`src/services/httpsCheck.ts`) | No |
| SSL Certificate Status          | Direct TLS probe                         | No |
| Domain Age                      | WHOIS API                                | Yes |
| Domain Registrar                | WHOIS API                                | Yes |
| Website IP Address              | Node DNS lookup + IP Geolocation API     | Geolocation only |
| Security Headers                | Direct HTTP fetch, header inspection     | No |
| Redirects                       | Direct HTTP fetch, manual redirect trace | No |
| DNS Information                 | Node DNS resolver (nameservers)          | No |
| Malware & Phishing Reputation    | VirusTotal API                           | Yes |
| Community Scan Verdict          | URLScan.io API                           | Yes |

Checks that don't need a key are still real, live checks — they just
use Node's built-in `tls`/`dns`/`fetch` instead of a paid API. This
keeps the report useful even before every key is configured.

## AI explanation

Every report includes an `aiExplanation` object — a beginner-friendly
summary generated by calling Claude (`src/services/aiExplanation.ts`)
with the check results. It answers: is this site safe, why, what
risks were found, and what to do next.

If `ANTHROPIC_API_KEY` isn't set, the call fails, or the model's
response doesn't parse into the expected shape, it falls back to
`src/services/aiExplanationFallback.ts` — a rule-based version built
from the same check data, in the same `{ verdict, reasons, risks,
nextSteps }` shape. Either way `generatedByAi` tells the frontend which
one it got, but the card itself always has something to show.

## Authentication

Signing up, logging in, and saving scan history all work with zero
external services — no third-party auth provider needed.

- `POST /api/auth/register` — `{ name, email, password }` → `{ token, user }`
- `POST /api/auth/login` — `{ email, password }` → `{ token, user }`
- `GET /api/auth/me` — requires `Authorization: Bearer <token>` → `{ user }`

Passwords are hashed with Node's built-in `scrypt` (`src/utils/passwords.ts`)
— never stored in plaintext, and compared with a timing-safe check.
Sessions are a minimal hand-rolled HS256 JWT (`src/utils/jwt.ts`), signed
with `JWT_SECRET`. If `JWT_SECRET` isn't set, the server generates a
random one at boot instead of refusing to start — fine for local dev,
but it means every restart invalidates existing sessions until you set
a real one in `.env`.

`POST /api/scan` accepts an *optional* `Authorization` header
(`middleware/auth.ts`'s `attachUserIfPresent`): scanning still works
for anonymous visitors, but if a valid token is present, the completed
report is automatically saved to that user's history.

## Scan History

All routes below require `Authorization: Bearer <token>` and only ever
return/modify the calling user's own scans.

- `GET /api/scans?search=&sortBy=date|score&sortDir=asc|desc` — list, summary fields only (no full report, keeps the list payload small)
- `GET /api/scans/:id` — full saved report, for "Open previous reports"
- `DELETE /api/scans/:id` — removes a scan

Each saved record stores the exact fields requested (URL, date, risk
score, HTTPS status, overall recommendation, and a rolled-up API
results summary like `"8 safe · 1 caution · 1 unavailable"`) *plus*
the complete original report, so reopening a past scan doesn't
require re-scanning the site — it shows exactly what was found at the time.

## Data storage

Both users and scan history are stored in `server/data/*.json` — a
tiny embedded JSON-file database (`src/services/db.ts`), not a real
DB server. This keeps the project runnable with zero external setup.
Writes are serialized through a queue so concurrent requests can't
corrupt the file. This is the right tradeoff for this stage, but it
won't scale past a single server instance — swap `JsonFileStore` for a
real database (Postgres, SQLite, etc.) by reimplementing its
`read()`/`write()` methods; `userStore.ts` and `scanHistoryStore.ts`
only depend on that interface, not the file format.

`server/data/` is gitignored — don't commit real user data.

## Resilience

- **Missing key** → that check returns `status: "unknown"` immediately, no network call attempted.
- **Slow or failing API** → every external call goes through `fetchWithTimeout` (default 6s) and is wrapped in try/catch; a failure becomes an `"unknown"` result, never a thrown error.
- **Unexpected error anywhere** → caught by `middleware/errorHandler.ts`, logged, and answered with a safe 500 — the process itself never crashes (see the `unhandledRejection`/`uncaughtException` handlers in `src/index.ts`).
- **Partial results** → `meta.partial` and `meta.unavailableChecks` tell the frontend exactly which checks didn't complete, so it can say so instead of pretending the report is complete.

## Caching

Results are cached in memory per normalized URL for `CACHE_TTL_MINUTES`
(default 15). A cache hit skips every external API call and returns
instantly with `meta.cached: true`. See `src/services/cache.ts` — it's
a small `Map`-based TTL cache; swap it for Redis if this ever runs
across multiple server instances.

## Logging

All API failures go through `src/services/logger.ts`, which timestamps
and structures each entry (`[timestamp] [ERROR] message {context}`) so
they're easy to grep in production logs. Swap the transport there to
ship logs somewhere else without touching call sites.

## Resume Privacy Scanner

A second, independent feature alongside the Website Scanner — analyzes an uploaded resume PDF for personal information that's often unnecessary (and sometimes risky) to share publicly.

- `POST /api/resume/analyze` — multipart upload (field name `resume`), optional auth. Extracts text, detects PII, scores privacy, generates an AI review, and (if signed in) saves the report.
- `POST /api/resume/export` — generates a PDF from a report object directly in the request body, so guests can export without an account.
- `GET /api/resume/reports`, `GET /api/resume/reports/:id`, `DELETE /api/resume/reports/:id`, `GET /api/resume/reports/:id/export` — all require auth, all scoped to the calling user.

**How it works:**
- **Upload**: `multer` with memory storage (`middleware/uploadResume.ts`) — the file buffer exists only in RAM for the request's lifetime. It's never written to disk, so there's no temp file to clean up and nothing left behind if the process crashes.
- **Extraction**: `pdf-parse` reads the buffer directly (`services/pdfTextExtraction.ts`). A corrupt or password-protected PDF returns a friendly 422, not a crash.
- **Sanitization**: `utils/sanitizeText.ts` strips control characters and caps length before the text is analyzed, stored, or sent anywhere.
- **PII detection** (`services/piiDetection.ts`): regex/heuristic detectors for phone, email, LinkedIn, GitHub, portfolio links, personal sites, date of birth, and government ID numbers (masked immediately, never stored or returned in full). This is honestly a heuristic, not real NLP — address and date-of-birth detection in particular can have false positives/negatives on unusual formatting.
- **Scoring** (`utils/privacyScore.ts`): penalized per category *present*, not per occurrence — contact info and professional profile links cost nothing; a full address, birth date, or government ID cost the most.
- **AI review** (`services/resumeAiReview.ts`): same Claude integration pattern as the Website Scanner's AI explanation, with a rule-based fallback. Only category labels/counts are sent to the AI — **the raw resume text never leaves this analysis step**.

## Email Phishing Analyzer

A third independent feature, alongside the Website Scanner and Resume Privacy Scanner. Analyzes pasted email text, a raw header block (advanced mode), or an uploaded screenshot for common phishing tactics.

- `POST /api/email/analyze` — multipart, optional auth. Fields: `inputMethod` (`text`/`headers`/`screenshot`), `content` (text/headers modes), `screenshot` (image file), `attachment` (optional, metadata only — see below).
- `POST /api/email/export` — direct PDF export from a report object, works for guests.
- `GET /api/email/reports`, `GET /api/email/reports/:id`, `DELETE /api/email/reports/:id`, `GET /api/email/reports/:id/export` — all require auth, scoped to the calling user.

**Detection** (`services/emailIndicators.ts`) is regex/keyword-based, not a trained classifier — it catches well-known tactics (urgency phrases, credential/payment requests, sender/Reply-To mismatches, brand impersonation against a small known-domain list, SPF/DKIM/DMARC failures in headers mode, shortened or IP-based links) but sophisticated phishing can still slip past keyword matching. This is the same honest tradeoff as the Resume Scanner's PII detection.

**Link analysis deliberately does not duplicate the Website Scanner.** Extracted links only get lightweight, locally-computed flags (HTTPS, shortener, IP-based) — no VirusTotal/URLScan/WHOIS calls happen here. Clicking "Analyze this link" in the UI navigates to `/dashboard/url-scanner?url=...`, which `WebsiteScannerPage.tsx` reads on mount to auto-run a real scan through the existing pipeline.

**Screenshot mode** uses `tesseract.js` for OCR (`services/screenshotOcr.ts`) — genuinely lower accuracy than pasted text, and it downloads English language training data on first use (needs internet access the first time it runs). A low-text result surfaces a clear warning rather than silently analyzing near-empty text.

**Attachment handling** is metadata-only by design: filename, MIME type, and size, checked against a short list of risky patterns (executable extensions, double extensions like `invoice.pdf.exe`). The file's actual contents are never scanned — the UI states this plainly rather than implying malware detection that doesn't exist.

## Password Security Center

**This feature has no analyze endpoint, deliberately.** Every other
tool in CyberSentinel sends its raw input (a URL, a resume, an email)
to this backend for analysis. Passwords are different: sending one
over the network — even to your own server, even over HTTPS — is
exactly the kind of habit this feature exists to discourage. So
password strength analysis, the password generator, and the passphrase
generator all run **entirely client-side** (see the frontend's
`src/utils/passwordAnalysis.ts`, `passwordGenerator.ts`, and
`passphraseGenerator.ts`). This server never sees a password.

What this backend *does* handle is saving the **result** of an
analysis someone already ran locally — a score, a rating, recommendation
text, and checklist booleans:

- `POST /api/password/reports` — saves an analysis result. Validates the request body strictly (`controllers/passwordController.ts`) rather than trusting whatever shape arrives — if a `password` field somehow showed up in a request here, it's simply not part of the accepted shape and would be ignored.
- `GET /api/password/reports`, `GET /api/password/reports/:id`, `DELETE /api/password/reports/:id`, `GET /api/password/reports/:id/export` — all require auth, scoped to the calling user, same pattern as the other history features.

`types.ts` has a comment at the top of this feature's section as a
guardrail for future edits: don't add a password field to any of
these types.

## Data Breach Checker

Checks an email address against [Have I Been Pwned](https://haveibeenpwned.com)'s v3 API — the legitimate, industry-standard service for exactly this purpose. Requires a paid `HIBP_API_KEY`; there's deliberately no fallback for this one (unlike the AI explanation), since a breach check without real data would be actively misleading rather than just incomplete.

- `POST /api/breach/check` — `{ email }`, optional auth, rate-limited (8 requests / 10 minutes per user or IP, on top of whatever HIBP's own key tier allows).
- `GET /api/breach/reports`, `GET /api/breach/reports/:id`, `DELETE /api/breach/reports/:id` — require auth, scoped to the calling user.
- `PATCH /api/breach/reports/:id/actions/:actionId` — toggles one action-plan checklist item.

**Privacy notes:**
- HIBP returns a 404 for "no breaches found" — this is treated as a valid, successful result, not an error.
- Saved reports store a **masked** email (`j***@example.com`), never the full address — a privacy-by-design choice beyond what was strictly required.
- The AI explanation (`services/breachAiExplanation.ts`) only ever receives breach *summaries* — counts, categories, dates — never the email address itself.
- No leaked passwords are ever stored or displayed; HIBP's own API doesn't return them either, so this holds true architecturally, not just by convention.

**Scoring** (`utils/exposureRiskScore.ts`) is fully transparent — every point value is a named constant, and the report includes a `factors` array explaining exactly why the score is what it is, shown in the UI's "How is this score calculated?" section.

**Cross-feature integration**: `BreachReport.tsx` on the frontend links to the Password Security Center when a breach reported exposed passwords, and to the Email Phishing Analyzer otherwise — both with the caveat language the spec required, rather than overclaiming a causal link.

## CyberSentinel Security Center

The aggregation layer — combines existing results from all five other features into one profile. **Makes zero new external API calls.** Every stat comes from reading the same `list*ForUser` functions the other features' own history pages already use (`scanHistoryStore.ts`, `resumeHistoryStore.ts`, `emailHistoryStore.ts`, `passwordHistoryStore.ts`, `breachHistoryStore.ts`) — the only network call this feature ever makes is the one optional AI summary request.

- `GET /api/security-center/profile` — requires auth. Accepts `?refresh=true` to bypass the cache.

**Scoring is fully transparent** (`utils/securityScore.ts` + `utils/securityCategories.ts`): the overall score is a simple average of every category that *has data*, each weighted equally. A category with no activity is excluded entirely, never scored as 0 — the full methodology is returned in the response (`scoringMethodology`) and rendered in the UI's "How is this calculated?" section.

**The "Cybersecurity Education" category always reports no data** — there's no Learning Hub yet to generate real completion stats, so rather than fabricate a proxy score, it's permanently excluded from the overall score and never generates a recommendation, clearly labeled "coming with the Learning Hub."

**Achievements** (`utils/securityAchievements.ts`) are tied to real saved results in each feature's history — never to opening a page. "Security Learner" stays locked until the Learning Hub exists.

**Caching**: results are cached per-user for 3 minutes using the project's existing generic `TTLCache` class (same one the Website Scanner uses) — no new caching mechanism was built.

**Resilience**: if any one of the five history stores fails to load, the others still render; the response includes `partial: true` and the exact `"Some security information is temporarily unavailable"` message, rather than failing the whole page.

**What's intentionally not built**: a synthetic "overall score over time" trend line. Retroactively reconstructing what the overall score *would have been* at each past moment would require aligning five differently-timed, differently-weighted data sources — doing that convincingly risked implying more precision than the data actually supports. Per-category trends (Website Risk, Privacy Score, Phishing Awareness, Password Security Score) use each category's own real historical scores directly, and only appear once a category has 3+ data points.

## Cybersecurity Learning Hub

An interactive education platform — lessons, quizzes, XP, levels, streaks, and achievements. This is the feature that finally gives the Security Center's "Cybersecurity Education" category real data (it was a permanent placeholder before).

**Content is a static, versioned module, not a database table** (`data/learningContent.ts`). Lesson content is curated and publicly readable, so there's no user-generated content to justify a mutable store — adding a future lesson means adding one object to that file. Of the 40 lessons across all 7 categories your spec listed, 14 (two per category) have full, real content and working quizzes; the other 26 exist with complete metadata but `isAvailable: false`, shown as "Coming Soon" in the UI rather than either omitted from the path or shipped as shallow, low-quality stubs.

**Anti-cheat is enforced server-side, not just described:**
- `utils/sanitizeLesson.ts` strips every quiz choice's `isCorrect` flag and `explanation` before a lesson is ever sent to the client — the answer key never leaves this server before submission.
- `utils/quizGrading.ts` grades submitted answer indices against the real answer key entirely server-side.
- `services/learningProgressStore.ts` awards XP through idempotency keys (`lesson-complete:{id}`, `quiz-xp:{id}`, `category-complete:{id}`) — retrying a quiz updates your best score but cannot grant XP twice. This is the actual mechanism behind "prevent obvious duplicate rewards," not just a rate limit.

**Endpoints:**
- `GET /api/learning/catalog` — public (optional auth includes your own per-lesson status inline). Supports `?search=`, `?difficulty=`, `?category=`.
- `GET /api/learning/lessons/:id` — public, returns the sanitized lesson (no answer key) plus prev/next navigation.
- `POST /api/learning/lessons/:id/complete` — requires auth. Idempotent.
- `POST /api/learning/lessons/:id/quiz` — requires auth. Body: `{ answers: number[] }` (selected choice index per question). Grades server-side and returns full explanations.
- `GET /api/learning/profile` — requires auth. Returns XP, level, streak, category progress, and achievements.

**"Row Level Security" honesty note**: the spec asked for RLS, a Postgres/Supabase-specific feature. This project has never used a relational database — every feature, including this one, uses the same JSON-file-store pattern with manual per-user filtering (`userId` scoping on every read/write, enforced by `requireAuth` middleware). That's the actual equivalent protection this stack has, just not literally implemented as SQL Row Level Security, since there's no SQL database here to apply it to.

**Security Center integration is real, not just described**: `utils/securityCategories.ts`'s `calculateEducationCategory()` now takes real completion stats and computes an honest score — never a fabricated one, and it explicitly states that "learning progress ... doesn't by itself prove your accounts or devices are technically secure," per the spec. `utils/securityAchievements.ts`'s "Security Learner" achievement, previously hardcoded to always-locked, now unlocks on real lesson completion. Three pre-existing Security Center tests that encoded the old "always locked / no data" behavior were updated to reflect the new, correct behavior — not left silently broken.

## Threat Intelligence Dashboard

Routes live at `/threat-intelligence` and `/threat-intelligence/:id` — deliberately top-level, not under `/dashboard/*`, matching the spec exactly.

**Two genuinely different data sources, and it matters which is which:**
- **Live**: CVE/vulnerability data comes from [NVD](https://nvd.nist.gov) (`services/nvdApiClient.ts`), the official, legitimate US government vulnerability database your spec named. Cached 15 minutes via the project's existing `TTLCache`. Works without an API key at a lower rate limit; an optional `NVD_API_KEY` raises it.
- **Curated**: the phishing/malware/social-engineering "trend" entries (`data/threatContent.ts`) are NOT live-scraped. There's no single reliable free API for "current phishing trends" the way NVD exists for CVEs, so rather than scrape an unreliable source or invent statistics, these describe real, well-documented threat patterns (MFA fatigue, quishing, ransomware-as-a-service, etc.), each citing a genuine public source (CISA, FTC, FBI IC3, FCC, USPS). This is curated educational content, refreshed by developers — the code comments say so explicitly, and so does this README.

**Honesty note on the NVD integration**: it's written against NVD API v2.0's publicly documented response schema, but has not been verified against a live call in this environment (no network access here). CVE parsing fails closed — a malformed record is skipped, never shown as broken/partial data or crashed on.

**Every overview number traces to something real** (`utils/threatOverview.ts`): "Threats Tracked" counts our own curated entries; "Critical Vulnerabilities" is a live NVD count that reports `null` (shown as "Data temporarily unavailable") rather than a stale or fabricated number if that fetch fails.

**CVSS severity uses the real, standard scale** (`utils/threatSeverity.ts`) — 9.0+ critical, 7.0+ high, 4.0+ medium — not an invented threshold.

**Endpoints:**
- `GET /api/threats/overview`, `GET /api/threats` (curated list, filter/search/sort), `GET /api/threats/cves` (recent, cached), `GET /api/threats/cves/search?q=` (rate-limited, hits live NVD) — all public.
- `GET /api/threats/:id` — public; auto-detects a CVE ID vs. a curated slug by format. Records view history and returns bookmark state if authenticated.
- `POST/DELETE /api/threats/:id/bookmark`, `GET /api/threats/bookmarks`, `GET /api/threats/history`, `DELETE /api/threats/history` — require auth.

**Security Center integration is real, not just described**: `threatIntelligence` (threats viewed/bookmarked) is a separate field on `SecurityProfileReport`, structurally excluded from the scored `categories` array — per the spec's explicit instruction not to treat threat-intel engagement as proof of security.

## Security Analytics & Reporting Center

Route lives at `/analytics` — top-level, matching the spec exactly. This feature is almost entirely an aggregation and time-series layer: it introduces no second scoring system, and reuses the Security Center's category calculators (`calculateWebsiteSecurityCategory`, etc.) and recommendation generator directly, by import — not by reimplementation.

**The one genuinely new piece of infrastructure**: `services/securityScoreSnapshotStore.ts`. The Security Center only ever computes a *live* score — it never stored history, so an honest "Security Score Trend" chart wasn't possible without something new. A single additive line was added to the *existing* Security Center controller (`securityCenterController.ts`) that records at most one snapshot per user per day as a side effect — it doesn't change that endpoint's response or behavior at all. This means real trend data only exists going forward from when this shipped; new and existing users will see the spec's own prescribed empty state ("Complete two or more security checks to see trends") until snapshots accumulate. That's intentional, not a bug.

**A documented performance tradeoff**: the underlying history stores (scan, resume, email, password, breach) are local JSON files with no server-side date-range query support — adding that would mean rebuilding stores the spec said not to touch. Time-range filtering happens in memory on already-fetched data instead. Two spec-requested fields ("most common privacy findings," "common detected indicators") aren't present on the lightweight history summaries used everywhere else in the app — reconstructing them would require fetching every individual record, which the spec explicitly warned against. Instead, this substitutes the closest real data the summaries already contain (rating/classification distribution), documented in `utils/analyticsAggregation.ts` rather than silently narrowed.

**Endpoints** (all require auth, all scoped to `req.userId` from the authenticated session — never a client-supplied ID):
- `GET /api/analytics?range=` — the full dashboard: overview, score trend, category trends, all six per-feature analytics sections, improvements, insights, top priorities, and AI summary.
- `GET /api/analytics/compare?previous=&current=` — two-period comparison.
- `POST /api/analytics/report` — generates report JSON for a given range.
- `GET /api/analytics/report/export?range=` — same report, rendered as a PDF using the exact same pdfkit architecture as every other export in this app (`resumePdfExport.ts`, `emailPdfExport.ts`, `passwordPdfExport.ts`) — a new content layout, not a new PDF system.

**Report contents are deliberately conservative**: no passwords, no leaked credentials, no raw breach data — only the same category scores, recommendations, and summarized counts already shown on the dashboard.

## AI Security Coach

Route lives at `/ai-security-coach` — top-level, matching the spec exactly, and reachable from an "Ask AI Security Coach" link already added to the Security Center, plus "Explain This Result"/"Ask AI to Explain" buttons on the Website Scanner, Password Security Center, Data Breach Checker, and Email Phishing Analyzer.

**Architecture decision made explicit up front**: there is deliberately no `ConversationStore` or `MessageStore`. The spec said not to automatically persist every conversation, and to give the user full control if persistence exists at all — the simplest, safest reading of that is not to persist conversation *content* server-side at all. The frontend holds messages in React state only; each request sends a capped slice of recent turns (`MAX_HISTORY_MESSAGES = 10`) back for context. Only privacy-safe **usage counts** are stored (`services/aiCoachUsageStore.ts`) — conversationsStarted/questionsAsked/lessonsOpened/toolsOpened, never message text. "Deleting a conversation" is simply clearing frontend state; there's nothing server-side to delete.

**`services/securityContextService.ts`** builds focused context — never the user's entire history — by importing the exact same calculators the Security Center, Learning Hub, and Threat Intelligence already use. Every value in the resulting context string is a score, count, rating, or masked identifier already surfaced elsewhere in the app; nothing raw (no email body, no resume text, no password, no leaked credential) is ever included. Topic detection (`utils/aiCoachTopics.ts`) decides which sections to include based on keywords in the question, plus an explicit `explain` request from a UI button that force-includes a specific section regardless of keyword match.

**Recommendations are structurally guaranteed valid, never AI-invented**: the same topic detector maps to a fixed, server-controlled list of real Learning Hub lesson IDs (only ones marked `isAvailable`) and real tool routes. The AI is explicitly instructed not to fabricate its own links — the app attaches the structured recommendation independently of what the model says.

**Prompt injection defense** is implemented at two levels: the system prompt explicitly instructs the model to treat both the "Verified CyberSentinel Data" context and the user's own message as data to inform an answer, never as instructions — even if either contains text that looks like a command. The user message and context are also wrapped in explicit `<verified_cybersentinel_data>`/`<user_question>` delimiters in the actual API call, reinforcing the same boundary at the message level, not just in the system prompt.

**Endpoints** (all require auth, scoped to `req.userId`):
- `POST /api/ai-coach/message` — rate-limited (15/minute). Body: `{ message, history, explain? }`.
- `POST /api/ai-coach/track/lesson-opened`, `POST /api/ai-coach/track/tool-opened` — best-effort usage counters.
- `GET /api/ai-coach/usage` — the counters themselves.

**A real bug caught during this build, worth being upfront about**: while wiring the Security Center's "Ask AI Security Coach" link, it turned out that exact integration already existed in `SecurityCenterPage.tsx` from an earlier session — but two icons it referenced (`Bot`, `ArrowRight`) were never actually imported in that file. Every syntax check run throughout this whole project only checks parsing, not symbol resolution, so this latent bug was invisible to every previous check. It's fixed now, and a broader sweep across all 157 frontend files for the same class of bug (a capitalized JSX identifier with no corresponding import or local binding) found nothing else.

## Security Action Center

Route lives at `/action-center` — added to the top of the sidebar, right under Dashboard, since this is meant to become the new central hub. Reachable notification bell added to the existing (previously non-functional) topbar icon.

**Actions are computed live, exactly like the Security Center's score — there is no "Actions" database table of static rows.** `services/actionAggregationService.ts` rebuilds the full list on every request by importing and reusing every existing system: the Security Center's own category calculators and `generateSecurityRecommendations`, the password checklist, recent scan/email/breach history, the Learning Hub profile, Threat Intelligence bookmarks/history, and the Analytics improvement-trend logic. Nothing here is a second, competing system. The one thing that genuinely persists is the user's chosen **status** (not-started/in-progress/completed/dismissed), keyed by a stable `actionKey` string (e.g. `"enable-mfa"`) rather than a random id — so status survives across recomputations, and dismissing an action never touches or deletes the underlying scan/finding it came from.

**Deduplication is real, not just described**: `utils/actionDeduplication.ts` implements the spec's exact example — if both the Password Center's checklist and the Security Center's own recommendation flag the same `"enable-mfa"` action key, they merge into one action with `sources: ["password-center", "security-center"]`, keeping the *higher* of the two priorities, never averaged down. There's a dedicated test for this exact scenario.

**Priority is deterministic and documented, never AI-generated** (`utils/actionPriority.ts`): category scores below 40 are critical, 40–59 high, 60–79 medium, 80+ low; specific known-important gaps like a missing MFA checklist item are always at least high regardless of the aggregate score; threat-derived actions map one-to-one onto the Threat Intelligence Dashboard's own real CVSS-derived severity scale.

**Notifications are a genuinely new but justified piece of infrastructure** (`services/notificationStore.ts`, `notificationPreferencesStore.ts`), generated only as side-effects of three real events, added as small additive hooks into existing controllers — never a background job, since this app has no scheduler and one wasn't added just for this:
- A lesson completion that unlocks a **new** achievement (not every lesson — that would be spammy) → Learning Hub controller.
- A real, meaningful (≥5 point) Security Score improvement against a real prior snapshot → Security Center controller.
- A report actually being generated → Analytics controller.

Notification preferences gate whether a feed entry gets created, but never hide anything from the Action Center or Security Center themselves — a disabled category just means no separate notification, the real finding still shows up where it always did.

**Email notifications**: the schema has an `emailEnabled` field for forward compatibility, but it's a documented no-op — this app has never had an email provider, and the spec explicitly says not to introduce one just for this feature. The Settings UI says so plainly rather than presenting a working-looking toggle.

**A real gap found and fixed during this build**: Settings had been a full `ComingSoonPage` placeholder with nothing behind it. Since notification preferences needed a real home, I built a minimal, real `SettingsPage` — just the piece actually required, not a full account-settings rebuild — which also meant every placeholder route in the app has now been replaced with a real page, and `ComingSoonPage` itself is now fully unused (its import was removed).

## Testing

```bash
npm test
```

Runs the Vitest suite in `src/utils/__tests__`: URL normalization,
report aggregation (score/rating/band/confidence math, including the
0-floor clamp), and the recommendations engine. Like the frontend
suite, this is a starting scaffold — the untested surface most worth
covering next is the check services themselves (`services/*.ts`),
which would need their `fetch` calls mocked.

## Extending

Add a new check by writing a `services/yourCheck.ts` that returns a
`ScanCheckResult`, then include it in the `Promise.all` list inside
`controllers/scanController.ts`. The frontend maps unknown check `id`s
to a generic icon/explanation automatically, so nothing else needs to change immediately — though adding a matching icon and "Learn More" entry in the frontend's `scanService.ts` is a good next step.
